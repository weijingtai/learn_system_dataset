## 二、现状调查

### 2.1 当前数据中的标点分布

对全量 10 页数据扫描（`data_work/data/page_*.json`）：

| 指标 | 结果 |
|---|---|
| 含标点的行 | **1 行**（仅 page_001 第 2 列） |
| 标点字符总数 | **2 个**（全角括号 `（` `）`） |
| 标点种类 | 全角括号（FF08/FF09），无句号/逗号/顿号 |
| 框数≠字数的标点行 | **0**（括号均被正确识别为独立字框） |

该行完整文本："（宋）錢如璧撰"，7 字 7 框，括号各占独立框，置信度正常。

**用户所报的「如璧傳。」中的句号（。）在当前数据中不存在。** 可能原因：
- 原始 OCR 输出中 PaddleOCR 未检测到该句号（把它并入了前一个字的框）
- 用户在早期版本的数据上看到的问题，后续重跑已修复
- 该问题出现在其他书籍的数据中（当前仅装了 10 页样本）

### 2.2 标点在流水线中的处理链路

```
PaddleOCR 整行输出 → "如璧傳。"
       ↓
_clean_text() → ["如","璧","傳","。"]  ← 保留所有字符，包括标点
       ↓
segment_block() → 墨迹投影切段
       ↓
_align_to_count(seg_boxes, n=4) → 强制 4 段
       ↓
zip(seg_boxes, text_chars) → 一段配一字
```

**关键事实**：

1. **PaddleOCR 不为标点出独立检测框**：它输出整行文本 `rec_texts`，标点与汉字混在同一个检测框内
2. **墨迹投影可能漏掉标点**：句号 `。` 直径约 5-8px，墨迹极少，投影段可能被 `min_gap` 阈值过滤
3. **`_align_to_count` 兜底等分**：即使投影漏掉标点段，也会按字数强制等分，给标点分配一个「幽灵框」（几何位置是猜的，框内可能没有真实墨迹）
4. **诊断系统静默跳过**：`diagnose_page` 第 431 行 `if len(inside) != n: continue`，框数≠字数时直接跳过不报警

### 2.3 为什么当前数据没有问题

`_align_to_count` 的兜底等分保证了**字数恒等于框数**——标点永远不会被「丢掉」，它总有一个框。问题是：

- 框的几何位置可能是猜的（等分位置，不是真实墨迹边界）
- 框内可能没有真实笔画（空框）
- 诊断系统不检查这类「标点幽灵框」的质量

在当前 10 页数据中，唯一的标点是全角括号 `（` `）`——它们有足够的墨迹被投影检测到，所以不存在幽灵框问题。**但如果遇到句号 `。`、逗号 `，`、顿号 `、` 等小墨迹标点，幽灵框问题就会暴露。**

## 三、风险评估

### 3.1 实际影响

| 场景 | 影响 |
|---|---|
| 当前 10 页数据 | **无影响**（唯一的标点是括号，已正确识别） |
| 其他古籍数据（含大量句读标点） | **中等**：标点位置不准，但字不会丢、不错位 |
| 标点密集的近现代排版 | **较高**：句号/逗号密集出现时，多个幽灵框累积影响可读性 |

### 3.2 数据铁律检查

标点幽灵框**不违反**项目数据铁律：
- 不丢字：`_align_to_count` 保证每字（含标点）都有框 ✓
- 不覆盖：`orig_char` 正确记录 ✓
- 可追溯：审计链完整 ✓

唯一问题是**框几何可能不准**——但这属于质量问题，不是正确性问题。

## 四、处理方案（三个层次，由浅入深）

### 方案 A：诊断层增强（最小改动，推荐优先做）

**目标**：让诊断系统能发现标点相关的质量问题，而不是静默跳过。

**改动**：
1. `diagnose_page` 中 `if len(inside) != n: continue` 改为：框数≠字数时，检查差异是否由标点引起（差值 ≤ 标点字符数且差值 > 0 → 报告为 `punct_gap` 类型而非跳过）
2. 新增诊断信号 `punct_gap`：行文本含标点但框数 < 字数，提示「标点可能被并入相邻框」
3. 前端诊断面板展示 `punct_gap` 信号，提示用户手动检查

**测试**：构造含 `。` 的合成行，验证诊断能检出

**工作量**：~1 天

### 方案 B：投影层标点感知（中等改动）

**目标**：让墨迹投影能检测到小墨迹标点。

**改动**：
1. `segment_block` 中对最后一个投影段做特殊处理：如果该段对应行文本的最后一个字符是标点，尝试按标点的典型尺寸（5-15px）拆分
2. `symbol_gap_repair` 降低 `min_gap` 到 20px（当前 40px），专门针对标点级别的窄段
3. 新增 `_is_punctuation(char)` 工具函数，判断字符是否为常见标点

**测试**：合成含标点的竖排图，验证投影能切出标点段

**工作量**：~2-3 天

### 方案 C：OCR 后处理标点修复（较大改动）

**目标**：利用 PaddleOCR 的字符级置信度，识别并修复标点问题。

**改动**：
1. 在 `pipeline.py` 中，PaddleOCR 输出后增加标点检查：如果行文本最后一个字符是标点，检查该标点的 rec_score 是否异常低（标点置信度通常低于汉字）
2. 新增 `punctuation_repair` 函数：对已生成的 CharBox 列表，检查标点框的墨迹覆盖率，覆盖率过低时触发重新切分
3. 质量报告 `report.py` 增加标点识别率统计

**测试**：端到端测试含标点的完整流水线

**工作量**：~3-5 天

## 五、推荐实施路径

```
第一阶段（立即）：方案 A — 诊断层增强
  ↓ 用户确认标点问题确实存在
第二阶段（按需）：方案 B — 投影层标点感知
  ↓ 标点密集数据验证
第三阶段（可选）：方案 C — OCR 后处理修复
```

**理由**：
- 当前 10 页数据无标点问题，方案 A 足够覆盖诊断需求
- 方案 B 在有标点密集数据时才需要
- 方案 C 是长期优化，投入产出比需更多数据验证

## 六、验证方法

### 合成测试图

构造含标点的竖排古籍图（PIL 绘制）：
- 正常汉字（如「三辰通載」）+ 句号 `。`
- 验证 `segment_block` 能切出 5 段（4 字 + 1 标点）
- 验证 `_align_to_count` 后标点框位置正确
- 验证 `diagnose_page` 能检出标点问题

### 真实数据验证

在有标点的古籍数据上跑全流水线，检查：
- 标点是否被识别为独立字框
- 标点框的几何位置是否合理
- 诊断系统是否正确报告标点问题
