## 二、原始症状记录（均已修复；此节的根因判断多数有误，以 §七 为准）

### 问题1：竖排文字与框错位（反之亦然）
- **症状**：某列第N字的框位置正确，但框内识别出的是第N+1个字的内容；造成"字错位"或"后字顶掉前字"
- **根因**：PaddleOCR 竖排模式 `rec_texts` 与 `rec_polys` 索引对应关系混乱，已有的 `y_min` 重排不足以消除所有错位
- **受影响的页**：page_005、page_010 等密度不均的页
- **定位方式**：在 JSON 里检查 `page_0XX.json → chars → box['y']` 顺序与 `char` 内容是否匹配

### 问题2：多字一框（如"八一"合框，只认到"八"）
- **症状**："八一"被同一个检测框包住，segmentation 只切出有字的那一半，下字完全缺失
- **根因**：`segment_block` 沿 Y 投影切分时，第二段高度太小被 `_merge_thin_segments` 合并回上一段（阈值过宽）
- **典型位置**：page_005 左下角页码"481"的"八一"

### 问题3：假"口"字（连接笔画被当成独立字框）
- **症状**：两个字交界处的细微连接笔画被检测成独立框，rec 模型在那里只能识别出"口"或其他噪声字
- **根因**：PaddleOCR 检测器对竖排笔画的交界处敏感；`segment_block` 没有过滤这种极小框
- **当前状态**：尝试过滤 `w<8 && h<8` 仍不足以祛除，阈值需更仔细调节

### 问题4：文字分配循环取最后一个字（"琅玕"重叠）
- **症状**：某两个框的文字都显示"琅"，原真实的"玕"被覆盖成后面的字
- **根因**：旧版 `segment_page_chars` 代码有 `char = text_chars[-1]`（N+1个框拿到最后一个字）
- **当前状态**：已改成超出部分留空，但**尚未重跑验证**

### 问题5：竖排 Web UI 有框但无文字
- **症状**：右侧竖排译文面板空白（`columns` 有数据但前端不渲染）
- **根因**：疑似同一页面混入旧 book 的 cached data；前端 JS 画框/文字的绑定区域有 bug，空 char 的框不显示列
- **临时处理**：先重启 Web UI，若仍白页需看浏览器 console 报错

## 七、修复结论（2026-08-22 接手完成）

### 真实根因只有两条，不是五个 bug

原文 §二 把症状当成了 5 个独立问题并逐个调参，方向错了。实测根因两条：

**根因1 — 硬编码绝对二值化阈值**（对应问题5的"整行没文字"）
`segment_block` / `symbol_gap_repair` 用 `region < 128` 判墨迹。古籍背面透印字、
浅印字灰度在 176~229 之间，区域内**没有任何**像素 < 128 → 投影全空 → 返回 0 段
→ 调用方 `continue` 跳过 → 整行文字被静默丢弃。
实测 139 行零段，区域最暗像素 100% ≥128，吞掉 493 字。

**根因2 — 投影段按位置配字**（对应问题1「错位」+ 问题2「八一合框」+ 问题4「琅玕重叠」）
PaddleOCR 给的是**整行文本**，段边界是沿 Y 投影另算的，两者数量无任何约束关系。
「一」「二」「三」等横笔画字、「宫」「主」等内部有横向空隙的字会被切成多段
（实测「一二三」切出 6 段），而 `char = text_chars[si]` 按位置配字，于是从该字起
整列文字全部后移。**问题1/2/4 是同一根因的三种表现。**
实测 727 行中 360 行（49.5%）段数≠字数。

问题3（假「口」字）不是独立缺陷，是错位的副产品：修完根因2 后全10页只剩 1 个
「口」，在 conf=0.37 的行内，已被既有 low_conf 机制标记。

### 修法

| 提交 | 内容 |
|---|---|
| `c947c79` | 复现测试（红）：合成竖排图，不依赖 PaddleOCR |
| `87f7e8b` | `_ink_mask()` 按区域 2/98 分位数自适应定阈；`_align_to_count()` 配字前把段数强制对齐到字数；`_even_split()` 兜底 |
| `9e4d943` | Web UI 竖排面板列被 `overflow-y:hidden` 硬裁断 |

阈值 20 由真实数据定：139 个淡字行灰度极差 23~95，正常行 181~254，完全不重叠。

### 一个副作用要知道

## 八、用户实测反馈修复（2026-08-22 第二轮）

### 8.1 page_006 页码「四八二」框错

**症状**（用户报告）：「八」和「二」的上横被框成一个，「二」只剩下横看着像「一」。

**根因**：不在对齐逻辑里。投影本身**切对了** 4 段（四16px / 八15px / 二上横3px /
二下横4px），真凶是 `_merge_thin_segments` 把过细的段**无条件并进上一段**，不判断
上一段是不是另一个字。它的 `min_h_floor=4.0` 绝对下限还造成「3px 被并、4px 不被并」
的不对称，于是段数刚好并成 3 等于字数，对齐层无从察觉。

**修法**：删除 `_merge_thin_segments`，`segment_block` 改为直接返回投影墨迹段，
段→字合并统一交 `_align_to_count` 按字数做。
*为什么不是「改成并入较近的邻居」*：该例字内间隙(8px)与字间间隙(13/14px)量级相同，
换字号就翻车；合成图上方向还相反。**光看几何无法判断间隙是字内还是字间，只有
「已知这行有几个字」能判**——所以合并必须字数驱动。

修后：四 h16 / 八 h15 / 二 h15，「二」的框完整包住两横。

### 8.2 背面透印字被识别（一片黄框）

**症状**（用户报告）：纸张极薄，背面的字透过来也被识别了，大多标成黄色。

第一轮我选择保留并标 `extra.faint`，用户实测后证明这个取舍是错的。改为
**在识别前把透印从图上抹掉**（新增 `src/gujiorc/ocr/preprocess.py`）。

**为什么必须在识别前做**：事后过滤只能去掉纯幽灵行，修不了幽灵笔画与真笔画落进
**同一个检测框**时对真字识别的污染。实测「卷第七」被读成「卷第七吧」、整行读成
`'11'`/`'37'` 这类垃圾。

**可行的依据**：透印墨色与真墨**不重叠**。实测真墨的墨迹像素灰度 32~88，透印
116~240，中间 88~116 是干净空隙。把亮于 110 的像素推成纯白即可整块抹掉透印而
完全不碰真墨。

**淡印本防护**：每页打印「残留真墨 x%」（`kept_ink`），低于 1% 告警。
不能用「抹除比例」当告警——真笔画的抗锯齿边缘也落在被抹的灰度带里，正常页
抹除比例本来就有 3%~14%（第一版这么做误报了 6/10 页）。
正常页 `kept_ink` 实测 5.0%~12.3%，模拟淡印本 0.00%。
**淡印本/褪色本请用 `--bleed-thresh 0` 关闭或调低。**

**效果**：

| 指标 | 抹除前 | 抹除后 |
|---|---|---|
| 幽灵字框 | 531 | **0** |
| 正常页均置信度 | 0.69~0.96 | **0.95~0.97** |
| page_003 低置信行 | 44.2% | **0%** |
| page_003 生僻字 | 148 | **2** |
| page_001 生僻字 | 35 | **0** |

顺带解开了首轮报告里「page_010 生僻字 172/366=47%」的谜团——那不是生僻字，是透印。
识别质量也实质提升：`卷第七吧`→`卷第七`，还多认出 `周天黃道二十八宿求度數`、
`七政旺宮星度` 等原被幽灵覆盖的真文本。

Web UI 显示的仍是原图，所以透印肉眼可见但不再被当成内容——正是想要的效果。

## 九、人工校对编辑功能（2026-08-23 第三轮）

用户口述五点新需求：框 CRUD + Cmd+Z、鼠标框选多选、合并框、拆分框，以及第 5 点——
page_001「三辰通載」列的框↔字错位，问「这个功能你看一下要怎么做？」

**完整设计与实施记录见 `docs/PLAN_PROOFREAD_EDIT.md`。** 此节只记要点。

### 9.1 第 5 点的根因：第二轮的「段数==字数」契约测不到这一类

第二轮把「段数≠字数」压到 0/584（见 §8.4），但那只是**必要条件**。这一列里：

- 「三」的三横留白够大 → 被切成 2 段（多 1 段）
- 「通」「載」留白不足 → 被并成 1 段（少 1 段）

两个错误净效果为 0，契约满足、测试全绿，但从第 2 个框起每框都装着**下一个字**的识别结果。
行文本 `三辰通載` 本身 conf=1.00 完全正确，**错的只有段边界**。

> 教训：计数契约挡不住「一处多切 + 一处少切」的抵消型缺陷。这类只能靠几何判据发现。

### 9.2 修法：合并 → 拆分 → 重灌（三步，缺一不可）

逐框改字是错的解法：框还是错的（各装半个字），下游导出/重识别/向量化拿到的都是残缺字形。
有测试立此存照——单独重灌，结果与修复前逐字节相同。**必须先修几何。**

实测该列：三(h24)/辰(h9)/通(h58)/載(h131) → ①合并 → 三辰(h44)/通/載 →
②等分拆分 → 4 框各含一整字 → ③按行重灌 → 三/辰/通/載 各归其位。

### 9.3 自动诊断（否则要肉眼数几百个框）

`core/edit.py: diagnose_page()`，`pitch = 行长/字数`，三信号：
`over`(>1.6 pitch，跨字位该拆) / `thin`(<0.25 pitch，单笔画该并) / `drift`(框心偏移>0.6 pitch，真正的错位指标)。
**`thin` 单独出现不报警**——「一」「二」本身就矮。

实测波及 **41 / 532 行 = 7.7%**（page_001 4/4，page_010 20/81 = 24.7%）。

### 9.4.1 途中修掉的撤销栈瑕疵（已修）

原实现「先 push_history 再执行操作」，被闸门拒绝的请求（reflow 框数≠字数）也会在撤销栈
留一格相同状态——用户按一次 Cmd+Z 毫无反应。修法：`edit.py` 拆出 `snapshot_chars`（改动前抓）
与 `push_snapshot`（成功后才落栈），HTTP 六端点改为成功才落栈；`push_history` 保留为组合（兼容）。
`test_rejected_request_leaves_no_undo_entry` 钉死。HTTP 验收 19/19（含三次撤销=原状字段级）。

### 9.5 途中挖出的数据铁律漏洞（已修，值得记住）

`CharBox.from_dict` 的向后兼容兜底原为 `if not d.get("orig_char")`，
分不清「字段缺失（旧数据）」与「字段存在但故意为空」。`split` 拆出的框如实标未识别
（`orig_char=""`），一旦被 reflow/改字填上，**存盘再读就被兜底改写成「OCR 原本就认得这个字」**
——人填的字冒充机器识别，审计链断裂。改判 `"orig_char" not in d`，新增 3 个测试钉死。

> 这个坑是**新功能才让它可达**的：在此之前流水线不产出「orig_char 空而 char 非空」的框。
> 老代码不等于安全代码。
