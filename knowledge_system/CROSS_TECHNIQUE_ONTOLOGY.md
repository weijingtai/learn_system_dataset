# 跨技法术语本体设计（回答 v1.1.1 开放问题 #10）

> 2026-07-11 立。触发：签发第一个技法（bazi）术语表 v0 前，用户提出"多技法共享源数据 + 同形异义"问题。
> 对应 v1.1.1 §20 开放问题 #10「多术数共用本体的边界，以及术语同名异义的治理方式」——本文件即其答案。
> 也修正 v1.1.1 §5.3 的一处缺陷：该节把"受控术语表"整体划归"每种术数独立定义"，
> 未预见天干地支五行等全术数共享的源数据，导致各技法重复定义、同一个"甲"割裂成多个对象。

## 一、问题：术语在多技法间有三种关系，不能一刀切

用户观察（全部成立）：
- **共享源数据**：十天干、十二地支、地支藏干、五行、八卦、十二长生、九星、八神……各技法含义**完全一致**，是所有玄学技法的公共底座。
- **同形异义**：神煞（如驿马）、二十八宿、星曜……字面相同，但**八字 / 大六壬 / 七政四余里含义与用法不同**。
- **技法独有**：八字的十神/格局、奇门的门/宫……只在单一技法出现。

现状缺陷：concept_id = `co_<technique>_NNNNNN`，**按技法完全隔离**。后果——
1. 天干"甲"在 qimen 表是 `co_qimen_xxx`，在 bazi 表又是 `co_bazi_yyy`，系统认作两个无关对象（共享数据被重复造、无法统一维护）；
2. 同形异义词"驿马"在两技法各自独立编号，系统**不知道它们同名**，无法并列对比，用户搜索也聚不拢。

## 二、方案：术语分三层（L1 共享 / L2 同形异义 / L3 技法独有）

### L1 · 共享源数据层（shared canon）

- 存放：`schemas/shared/canon/`，一份全局表，**不隶属任何技法**。
- ID 规则：`co_shared_<domain>_NN`，如 `co_shared_stem_01`（甲）、`co_shared_branch_01`（子）、`co_shared_wuxing_01`（木）。
- 收录闭集（穷尽、不增长）：天干(10)、地支(12)、五行(5)、阴阳(2)、八卦(8)、地支藏干(映射)、十二长生(12)、纳音(60)等。
- 各技法术语表**引用**而非重定义：bazi/qimen 的"甲"都指向 `co_shared_stem_01`。
- **效率红利**：L1 是闭集，工位 4 可用**确定性字典匹配**（不耗模型），准确率 100%，且全技法只维护一份。

### L2 · 同形异义层（homograph with per-technique senses）

采用用户拍板的**"一词条多义项"**模型：

```yaml
# schemas/shared/homographs/驿马.yaml
surface: 驿马
homograph_id: hg_0042           # 字面共享的锚
senses:
  - concept_id: co_bazi_000042      # 八字义项
    technique_id: bazi
    gloss: 动象/迁移之神煞
    status: confirmed_v0
  - concept_id: co_liuren_000042    # 大六壬义项
    technique_id: liuren
    gloss: 天马/传递信息
  - concept_id: co_qizheng_000042   # 七政四余义项
    technique_id: qizheng
    gloss: 星曜名
```

- 字面（surface）共享一个 `homograph_id`；每个技法一个独立 `concept_id` + 独立义项。
- **工位 4/5 绑定的永远是带技法的 `concept_id`（义项），不是裸字面**——从源头杜绝跨技法串义。
- 检索"驿马"→ 命中 homograph → 并列展示各技法义项（正是用户要的对比阅读，也天然适配 §5.2 的"并列不同流派/技法立场"）。
- 二十八宿、九星、八神、神煞、星曜均走此层。

### L3 · 技法独有层（technique-private）

- 维持现状：`co_<technique>_NNNNNN`，存 `schemas/techniques/<t>/glossary_v0.yaml`。
- 八字十神/格局/调候、奇门门/宫等只此一家的词，留在各自技法表。

## 三、工位 4 提取时如何判层（提准确率与效率的关键）

术语识别按"先闭集、后开集"三步走，把机器能定的交给机器，只把真歧义交给模型/人工：

1. **L1 闭集匹配（确定性，免模型）**：先用 shared canon 字典扫一遍，天干地支五行八卦十二长生等直接命中、直接绑 `co_shared_*`。这批占比高、零歧义、零成本。
2. **L2 同形表比对**：命中 homograph 表里的字面（驿马、角宿…）→ **必须按当前技法选义项**，绑该技法的 concept_id；选不准 → uncertainties，不许裸绑字面。
3. **L3 技法新词**：都不是 → 进本技法候选/new_concept_candidates，走原流程。

## 四、落地步骤（增量，不推翻现有）

| 步 | 动作 | 影响面 |
|---|---|---|
| 1 | 建 `schemas/shared/canon/`，录入天干/地支/五行/八卦/十二长生等闭集，编 `co_shared_*` | 新增，不动存量 |
| 2 | 改 validate_glossary 的 ID 正则：接受 `co_shared_*` 与 `co_<t>_*` 两类 | 校验器兼容 |
| 3 | 建 `schemas/shared/homographs/`，先放已知同形（驿马等），随技法增补 | 新增 |
| 4 | 工位 4 INSTRUCTIONS 补"三步判层"；bazi 表里的天干地支候选改引 `co_shared_*` | 模板 + 存量迁移 |
| 5 | qimen glossary_v0 里的天干地支条目回迁到 shared（消除首例重复） | 一次性清理 |

## 五、对本次 bazi v0 签发的即时影响（重要）

**bazi 术语表 v0 现在先不要把天干地支单字固化为 `co_bazi_*`**——否则将来要迁移。首批 60 候选里的单字干支（甲/庚/申/子…）应标记为"待归 L1 shared"，**签发时只签 L3 技法独有词（十神/格局/调候）**，L1 词等 canon 建好后统一引用。这样第一个技法表从一开始就不含将来要返工的重复数据。
