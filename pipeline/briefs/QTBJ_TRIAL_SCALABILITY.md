## 三、开跑前已预见的三个结构性问题（盯住）

1. **命例识别是最大变量**（对应 H1）。SEG_009 用"≥2 干支组合"启发式，是**警告非硬拦截**——终判靠工位 5 语义。这是本次试运行最该验证的模型能力。
2. **吞吐瓶颈是人，不是模型**（对应 H3）。无 API key 模式下 41 批 ×（生产+复核+抽查）= 你粘几十次启动句。首批验证流程无误后，下一道坎是"OpenCode 能否一次连做多批"（牺牲隔离换吞吐），等首批数据再定。
3. **成本此刻全空白**（对应 G6）。首批跑完，batches.yaml 的 cost 字段出第一组真实 token/分钟数，成本模型才从占位变实数。

### 复核发现（程序校验抓不到、靠独立重核才发现的）

1. **切分粒度差异非缺陷**：b003 只切 2 段（四月 / 五六月），初看比 b002/b004 逐月更粗，核对原文确认——三夏甲木原文本就是"四月"和"五六月甲木"两个标目，无独立五月/六月条目。OpenCode 忠实原文结构，**正确**。教训：C 类条目数由原文标目决定，不可用"每月一条"的预期去套。
2. **命例判断准确**：命造举例（"若庚申、戊寅、甲寅、丙寅…发进士。或甲午日庚午时，此人必贵"）与通则（"得丙癸逢，富贵双全"）区分正确。H1 是本次最该验证的能力，**通过**。
3. **唯一真缺口是 token 成本**：manual 模式 run.yaml 的 cost.tokens 为空，OpenCode 未回传 usage。放量前需在启动句里要求 OpenCode 报告本次 token 用量，或接 API 模式自动记录。

### 关键结论：A 方案（自报 token）证伪，成本缺口只能走 B（API 模式）

第二轮启动句已按 A 方案要求 OpenCode 自报 token，OpenCode 回复"平台未暴露 token 接口"。
→ **token 成本无法在 OpenCode 手工模式下采集**。要拿到成本数据，只有等接入 DeepSeek V4 API（runner production 模式自动记 usage）。
→ 决策更新：token 成本从"放量前必补"降级为"接 API 时自然补齐"；在此之前，成本模型只有**人工分钟**一个维度（约 3 分/批复核），token 维度挂账等 API。这不阻塞切分工位继续放量。

### 复核方自查（记一次我自己的错误，值得留痕）

本轮我的核对脚本一度报 b008「覆盖=False」，虚惊。根因是**我把 b008 硬编码对到错误伪页 p0013**（b008 实为三秋乙木，p0013 是三冬乙木）。正确判据是 draft==input（gen_task.py 已保证 input 忠实取自原文），不该由复核脚本另用页码反推。教训：复核工具自身也要防"基准搞错"，验证覆盖统一用 draft vs input，不重新映射页码。

### 假设终判
- **H1 命例区分**：✅ 成立。命例密集的丙丁火/庚辛金条目全跑完，66 段 case 标注，独立复扫 0 漏标。这是本次最该验证的能力，**通过命例密集区考验**。
- **H2 path 继承**：✅ 成立。全书 path 月令继承无丢失（entry_title 曾丢字已修）。
- **H3/H4 人工与返工**：✅ 成立。返工集中在少数批，多为简繁/标点，非语义错。
- **token 成本**：✗ 仍空缺（A 方案证伪，待 API 模式）。

### 但这次"跑完"付出的代价，才是真正的可扩展性教训

41 批看似顺利，实则暴露了 **4 个流水线隐藏缺陷**，全部靠人工复核才发现——若无复核直接放量，会全部沉淀成质量债：
1. entry_title 丢字 41 处（脚本切分降质）→ 已加 SEG_010 硬拦截
2. **b001 无声漏跑（致命覆盖缺口）** → 已建 check_coverage 强制门
3. 修 draft 未重归档（审计不一致）→ 已立铁律
4. 五行总论类型判错欠切分（隐蔽）→ gen_outline 已自动判 B/C

### 可扩展性最终判断
**流水线本身可扩展（结构规整、模型判断准、忠实性零破损），但"无人复核的自动放量"此刻还不安全**——本轮 4 个缺陷有 3 个是校验器抓不到的（漏跑、类型判错、审计不一致靠脚本 PASS 蒙混）。现在这 3 类都补了程序化兜底（check_coverage / gen_outline 自动判型 / 归档铁律）。**结论：补丁落地后，下一本书可显著减少逐批复核、转向抽查+程序门；但每本书的"总论/导言"等非典型章节仍需人眼盯一次**（它们是本轮出错的集中地）。
