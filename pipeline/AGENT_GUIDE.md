# AGENT_GUIDE：接手本项目的 AI 必读

> 写给后续接手的 AI agent。假设读者能理解简单目标、执行简单命令，但复杂推理容易出错。
> 所以本手册只有：铁律、固定循环、查表修错。**不要求你自己判断，照做即可。**

## 一、六条铁律（违反任何一条 = 工作作废）

1. **一次只做一件事。** 一个任务 = 一个知识单元的一个文件，或一条明确命令。做完就停。
2. **只写自己被指派的文件。** 不碰 `corpus/` 下的任何文件（那是原始证据，只读）。不碰别的单元。
3. **原文只能复制粘贴，禁止手打。** 从 `corpus/.../transcript_v1.md` 里复制，一个字都不能改。繁体不能变简体（"難窮"≠"难穷"，差一个字校验就会失败——这是实测结论）。
4. **不知道原文在哪 = 不写。** 禁止凭自己的知识写任何术数内容。原文没说的，一个字都不许添。
5. **做完必须跑校验，PASS 才算完成。** 命令见下方循环。
6. **修两次还不过 = 停下报告。** 不许反复瞎试，不许为了通过校验而改原文或删主张。

## 二、标准工作循环（每个任务都一样）

```
第 0 步：读 pipeline/lessons/LESSONS.md 里"通用"＋你的工位对应小节（几十秒，能避开前人踩过的坑）。
第 1 步：读任务说明，确认要写哪个目录的哪个文件。
第 2 步：写文件（格式照抄 units/ku_qimen_000001/ 这个正确示范）。
第 3 步：运行校验（在 pipeline/ 目录下）：
        python3 validators/validate.py units/<你的单元目录名>
第 4 步：看结果。
        PASS → 输出一行报告："完成 <单元名>，校验 PASS"。结束。
        FAIL → 按第三节的表修错，回到第 3 步。最多修 2 次。
        修 2 次仍 FAIL → 输出报告："无法完成，剩余错误如下"＋粘贴错误原文。结束。
```

## 三、错误码修法查表

| 错误码 | 意思 | 怎么修 |
|---|---|---|
| SCH_001 | 缺文件或缺字段 | 对照 `schemas/core/SCHEMA.md` 把缺的字段补上；不知道填什么就填 `[]` 或停下报告 |
| SCH_002 | 枚举值写错 | 只能从 SCHEMA.md 第 5 节的 7 个状态词里选；新提取的内容一律填 `machine_extracted` |
| ID_001 | 编号格式错 | 对照错误信息里的格式要求改；数字必须 6 位，不够补零（`000001`） |
| ID_002 | 编号重复 | 换一个没用过的号；查已用的号：`grep -r "as_qimen_" units/` |
| SRC_001 | 来源文件缺失 | 停下报告，这不是你能修的 |
| SRC_003 | 哈希不匹配 | 停下报告，说明有人改动了原始文件，这是严重问题 |
| TXT_001 | 引用和原文不一致 | 回到转录文件重新**复制粘贴**那句话，不要手打 |
| REF_001 | 引用的对象不存在 | 检查编号拼写；如果证据片段还没登记，先在 provenance.yaml 里登记它 |
| SEM_001 | 主张没有证据 | 找到支持这条主张的原文句子，登记为证据片段并引用；**找不到原文就删掉这条主张**，不许硬凑 |

## 四、新建一个知识单元的分步操作

```
第 1 步：确定编号。查现有最大号：ls units/ 。新号 = 最大号 + 1（6 位补零）。
第 2 步：建目录 units/ku_qimen_0000NN/ 。
第 3 步：先写 provenance.yaml ——从转录文件里复制粘贴你要用的原文句子，
        每句一个 source_span_id（格式 ss_<书名>_ed01_p<页4位>_s<句2位>）。
第 4 步：再写 unit.yaml ——照抄正确示范的字段，span_ids 填第 3 步登记的所有编号。
第 5 步：最后写 assertions.yaml ——每条主张的 evidence 必须引用第 3 步里的编号。
        原则：先有证据，再有主张。顺序不能反。
第 6 步：跑校验（第二节循环）。
```

## 五、M1 搭建经验总结（为什么这样设计）

1. **简繁体是最大的坑。** 反样例实测：引用里一个"难"字（应为"難"）就导致 TXT_001。所以铁律 3 要求复制粘贴。模型默认输出简体，处理繁体古籍时必须显式要求保持原字形。
2. **"先证据后主张"的顺序能防住大部分编造。** 如果先写主张再找证据，模型会用自带知识凑；反过来先登记原文片段，主张就只能从片段里长出来。第四节的步骤顺序是故意的。
3. **校验程序是唯一裁判。** 它只报错不改内容，所以你不可能"骗过"它，只能真的改对。PASS 不代表内容语义正确（那是复核模型和人工的事），但 FAIL 一定代表有实际问题。
4. **状态词是权限不是装饰。** 新内容永远是 `machine_extracted`；只有另一个不同家族的模型复核后才能升 `cross_model_reviewed`；`expert_verified` 目前任何 AI 都无权使用。
5. **占位转录要在 manifest 里写明。** 当前 `src_yanbo_ed01` 的转录是 M1 测试用占位文本，正式底本登记后要升版（edition_note 里已注明）。任何 agent 不得把占位文本当成已核对的定本引用到正式产出里。
6. **规则只能有一个出处（M2 验收实测教训）。** M2 任务书重述了切分规则并写错（"8 句=8 段"），执行 agent 忠实照做，切出 4 个半联段。从此规矩：任务书只许**引用** HANDBOOK 章节号，不许复述规则内容；发现两份文档规则冲突 → 停下报告，以 HANDBOOK 为准。
7. **切分输出交付前必须跑 `check_segments.py`。** 人肉自查靠不住，程序抓半联/覆盖缺失是实测有效的（旧输出 4 处半联全部被抓出）。

## 五 A、写校验器／检查脚本的附加规矩（任务涉及 validators/ 时必须遵守）

校验器是别人的裁判，所以它自己要先过堂。写任何校验规则时：

1. **每条规则配一个负例自测**：故意造一个违反该规则的样本（在 /tmp 或临时副本上做，不动原件），喂给你的校验器，**FAIL 才算这条规则写完了**。正例 PASS 什么都证明不了。
2. **双向规则必须两个方向各写一条检查、各配一个负例**。"X 里必须有、Y 里必须没有"是两条规则不是一条——只实现一半等于没实现（实测教训：AST_002 首版只查了 merged 方向，单路 draft 伪造高状态照样放行）。
3. **汇报时必须贴出每个负例测试的命令和 FAIL 输出原文**。没有负例输出的校验器交付视为未完成。
4. 校验器只报错不修数据；发现自己需要"放宽规则才能让现有数据通过"→ 停下报告，不许放宽。

## 六、禁止清单（永远不做）

- 不删除、不修改 `corpus/` 下任何文件；
- 不修改校验程序 `validators/validate.py`（发现校验程序本身有 bug → 停下报告）；
- 不修改别人的单元来"解决"自己的编号冲突；
- 不用自己的术数知识补充原文没有的内容；
- 不把 `status` 填成 `cross_model_reviewed` 或更高（那需要独立复核流程）；
- 不在校验 FAIL 的情况下宣称任务完成。
