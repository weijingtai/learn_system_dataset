# L1 共享 Canon · 治理与修订规则

> 2026-07-11 立。配合 CROSS_TECHNIQUE_ONTOLOGY.md 的 L1 层。
> 核心矛盾：canon 是"闭集地基"（天干永远 10 个），又必须**可事后修改**（别名、藏干映射、注记会订正）。
> 解法照搬 v1.1.1 §6.2「稳定 ID + 修订」：**ID 永久冻结，内容按修订号演进，下游绑 ID+rev 不被静默破坏**。

## 一、三层都可修改，但改法不同

| 层 | 位置 | 可改什么 | 谁能改 |
|---|---|---|---|
| L1 共享 canon | `schemas/shared/canon/` | 别名、藏干映射、五行/阴阳属性订正、注记 | 需跨技法评审（影响所有技法） |
| L2 同形异义 | `schemas/shared/homographs/` | 增删义项、改某技法义项释义 | 该技法负责人改本技法义项 |
| L3 技法独有 | `schemas/techniques/<t>/` | 常规术语增删改 | 该技法负责人 |

## 二、修改铁律（三层通用）

1. **concept_id 永久冻结**：一旦分配，永不改字面、永不复用、永不删除。词废弃用 `status: deprecated`，不是删行。
2. **改内容必须升 `rev`**：每个概念有 `rev`（从 1 起）。任何内容变更 rev+1，并在 `rev_note` 记一句为什么。
3. **闭集完整性不可破**：canon 的闭集（天干必须恰好 10、地支恰好 12）由 check_canon 强制；增删闭集成员＝改标准，需专门决议，不走常规修改。
4. **下游绑 ID+rev**：工位 4/5 和注解引用 canon 时记 `concept_id` 与引用时的 `rev`；canon 升 rev 后，下游可择机同步，但旧引用不失效（指向历史 rev）。
5. **修改留痕**：每个 canon 文件有 `revisions:` 段，逐条记录 日期/改了什么/rev。

## 三、修改操作流程

```
1. 定位要改的概念（concept_id 不动）
2. 改其可变字段（aliases / hidden_stems / note …）
3. 该概念 rev+1，写 rev_note
4. 文件顶部 revisions 段加一行
5. 跑 python3 validators/check_canon.py schemas/shared/canon/ —— 闭集完整性+ID唯一+引用可解析必须 PASS
6. 若下游已有引用，评估是否需要同步（多数属性订正不影响已建主张）
```

## 四、为什么这样能兼顾"稳定"与"可改"

- APP 里用户点"甲"看到的 Tooltip、关联的主张、别人的注解，全绑在 `co_shared_stem_01` 这个**永不变的 ID** 上——所以你随时修订"甲"的释义、补别名，这些链接都不断。
- 而"甲属阳木"这种事实若发现录错，改字段 + 升 rev 即可，历史留痕、可追责、可回滚。
- 闭集完整性由程序守住，避免有人手滑把天干删成 9 个。
