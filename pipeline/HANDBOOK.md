# HANDBOOK：典籍整理完整操作手册 v1.0

> 读者：接手本项目任何工位的 AI agent。
> 读法：先读 `AGENT_GUIDE.md` 的六条铁律（永远适用）→ 打开你任务包里 `task.yaml` 的 `stage` 字段 → 跳到本手册对应工位章节 → 逐步照做。
> 本手册里所有"示意样例"仅用于教学，**禁止把手册里的例句当作原文引用**——你的原文只能来自任务包 `input/` 里的文件。

## 第 1 章 全局图：你在流水线的哪个位置

```
原书（PDF/扫描/外部转录）
   ↓
[工位1] 转录核对 ──→ 干净的逐字转录＋页码映射
   ↓
[工位2] 结构盘点 ──→ outline.yaml（大书必做，小段落可跳过）
   ↓
[工位3] 语义切分 ──→ segments（不改一字地切开）
   ↓
[工位4] 术语识别 ──→ concept_mentions（只许闭集匹配）
   ↓
[工位5] 主张提取 ──→ assertions（每条必须有证据；两个模型各做一遍）
   ↓
[工位6] 白话释义 ──→ content.md（标明"机器释义"）
   ↓
[工位9] 词条聚合 ──→ entries（不许消除流派冲突）
   ↓
校验程序 validate.py ──→ PASS 才算完成
```

你只负责自己的一个工位。上游给你什么就用什么，下游需要什么就按格式给什么，**不越位**。

## 第 2 章 通用工作协议（所有工位相同）

### 2.1 每个任务结束时必须输出 result.yaml

放在任务包 `output/` 目录，格式固定：

```yaml
task_id: task_qimen_000123
result: completed            # 四选一: completed / completed_with_warnings / blocked / failed
warnings: []                 # completed_with_warnings 时逐条列出
blocked_reason: ""           # blocked 时说明缺什么
uncertainties:               # 拿不准但没到阻塞程度的点
  - where: s03
    note: "「格」字疑为异体，按原样保留"
new_concept_candidates: []   # 工位4 专用
lesson_candidates: []        # 本任务发现的可复用经验（一句话规则），由复核方决定是否收入 lessons/LESSONS.md
needs_escalation: false      # true 时必须同时产出 ESC 文件（见 2.3）
```

经验固化规矩：agent **不直接写** `lessons/LESSONS.md`（防垃圾堆积）；候选经验放 result.yaml，验收时由复核方筛选收录。开工前必读 LESSONS.md 对应小节（AGENT_GUIDE 循环第 0 步）。

### 2.2 三级容错总则（遇到问题先分级，再行动）

| 级别 | 什么情况 | 你怎么做 |
|---|---|---|
| 一级：自己修 | 格式错、编号错、引用不一致等**校验程序能指出的错** | 按 AGENT_GUIDE 第三节查表修，最多修 2 次；修好继续 |
| 二级：阻塞 | 缺上下文（指代不明、前提在任务包之外）、输入文件损坏、疑似缺页 | 停止本任务，result 填 `blocked`，写清缺什么。**禁止猜。** |
| 三级：升级人工 | 语义拿不准且影响结果：两种读法都通、正文注文分不清、疑似原书刻误、流派归属矛盾 | 产出 ESC 文件（见 2.3），该条目标记 `disputed`，**其余部分继续做完**。不要因一处争议废掉整批。 |

判断口诀：**校验器能查的自己修；缺材料的停下要；拿不准语义的留给人，但只留一个最小问题。**

### 2.3 升级人工的 ESC 文件格式

放在 `pipeline/escalations/ESC_<任务号>_<序号>.yaml`。人工只有几分钟，必须做成"看一眼就能选"：

```yaml
esc_id: ESC_task_qimen_000123_01
task_id: task_qimen_000123
where: ss_languang_ed01_p0031_s04
original_text: "（把那句原文逐字贴在这里）"
context_before: "（前一句）"
context_after: "（后一句）"
question: 此句的"火"指丙火还是泛指火，两读会导致主张的条件不同
options:
  - A: 指丙火（依据：上文刚论丙）
  - B: 泛指火（依据：本节通论火性）
  - C: 不确定，标记 disputed 保留两读
impact: 影响 as_bazi_000045 的 conditions 字段
```

规矩：一个 ESC 只问**一个**问题；必须给选项；必须贴原文，不许只给你自己的转述。

### 2.4 编号防冲突：先领号段，再干活

多个任务并行时编号会撞车。规则：

1. 每个任务包的 `task.yaml` 里由派发者写好 `id_range`（如 `ku_bazi_000200 到 000299`）；
2. 你只能用自己号段内的编号；
3. 号段用完 → result 填 `blocked`，blocked_reason 写"号段耗尽"；
4. `task.yaml` 里没有 `id_range` 又需要新编号 → 同样 blocked。**禁止自己挑一个"看起来没人用"的号。**

## 第 3 章 文本类型判定（处理大书的第一个关键）

不同类型的古书切法完全不同。动手前先判类型，判错类型整批返工。

| 类型 | 特征 | 例子 | 切分单元 |
|---|---|---|---|
| A 韵文歌诀 | 整齐押韵，五言/七言，节奏强 | 《烟波钓叟歌》《滴天髓》正文 | 按联（两句）或按完整意群，一联一段 |
| B 论说散文 | 大段议论，无韵，论点接论据 | 《渊海子平》各论、子平类命理书 | 按论点切：一个完整论点＋其论据 = 一段；换论点就切 |
| C 条目/表格 | 重复的结构模式：条目名＋解说；或纯表 | 《穷通宝鉴》（拦江网）十干×十二月体例、《三辰通载》神煞历表、《星命指南》星曜条目 | 按条目切，一条一段；表格转成结构化列表（见 3.2） |
| D 注疏混排 | 正文夹注解，字号/缩进/"注曰""解曰"区分 | 各种笺注本 | 先分层（正文层/注文层），再在层内按 A/B/C 切 |

判定方法（按顺序检查，命中即停）：

1. 有"注曰、疏云、解曰、批注"或明显正文夹小字 → **D**，先分层；
2. 通篇五言/七言整齐押韵 → **A**；
3. 出现重复的结构模板（"正月甲木……二月甲木……"或"某星：主某事"）→ **C**；
4. 都不是 → **B**。

在 result.yaml 的 warnings 里写明你判定的类型和依据，一句话即可。

### 3.1 类型 B（论说散文）切分细则——最容易做错

- 通过标准：每段是一个**能独立成立的论点**；把这段单独给人看，人能明白它在主张什么；
- 常见错误一：按固定字数切 → 论点被腰斩，**不通过**；
- 常见错误二：整章不切一大段 → 下游主张提取会漏，**不通过**；
- 段与段之间允许"承上"字样（"故""是以"），但被承接的内容必须已在前段完整出现；
- 一段的合理长度大致 50–300 字。超过 300 字先检查是不是包含两个论点。

### 3.2 类型 C（条目/表格）细则

- 条目式（穷通宝鉴体例）：一个条目 = "标目＋正文＋（若有）注"，整体一段，不拆散；
- 表格：转成 YAML 列表，每行一条，**保留原表的行列标题原文**，并在 note 里注明"原为表格，行列结构如下"；
- 通过标准：从你的结构化结果能还原出原表，不多不少；
- 不通过：把表格压成一段连续文字（行列关系丢失）。

### 3.3 类型 D（注疏混排）细则

- 每段必须带 `layer` 字段：`main`（正文）或 `commentary`（注文），注文再带 `commentator`（注家名，原书没写就填 `unknown`，禁止猜人名）；
- 正文和注文**分开编段号**，注文段记录它注的是哪个正文段（`attached_to: s03`）；
- 分不清某段是正文还是注文 → 这就是三级容错，出 ESC，选项给"A 正文 / B 注文 / C 存疑"；
- 不通过的典型：把注家的话切进正文段里（这会让下游把注家观点当成原书主张——本项目最严重的语义错误之一）。

## 第 4 章 大部头书籍的处理流程

《三辰通载》《星命指南》《拦江网》这类书几十万字，和四联歌诀完全不同。规则：

### 4.1 铁则：大书永远先做结构盘点（工位2），再做其他一切

产出 `outline.yaml`，示例结构：

```yaml
work: 穷通宝鉴
outline:
  - node_id: n001
    path: 卷一 / 论木 / 正月甲木
    pages: [12, 14]          # 起止页
    text_type: C             # 第3章的类型
    est_chars: 800
    status: pending          # pending / in_progress / done
```

通过标准：每个叶子节点 ≤ 一个自然结构单元（一节/一个条目组）；每节点有页码范围和类型；全书页码无缺口无重叠。
不通过：节点粒度到"卷"就停（太粗，一卷几万字没法当任务包）；页码范围重叠或跳页без说明。

### 4.2 分批规则

- 一个任务包 = outline 的一个叶子节点；单节点超过 **2500 字**再对半切，切点必须在段落边界；
- 每个任务包的 `input/` 除正文外必须带三样上下文：
  1. `context_before.md`：上一批末尾约 200 字；
  2. `path.txt`：卷章路径（"卷一/论木/正月甲木"）；
  3. `glossary.yaml`：本书已确认的术语表快照（工位4 用，工位5 参考）；
- 你只处理 `input/text.md`，上下文只用来理解指代，**不进入你的输出**。

### 4.3 批次账本 batches.yaml（断点续跑的关键）

每本书根目录一份，由派发者维护、每个 agent 完工时更新自己那一行的 status：

```yaml
batches:
  - batch_id: qtbj_b012
    node_id: n001
    task_dir: tasks/task_bazi_qtbj_b012_seg
    id_range: [ku_bazi_000200, ku_bazi_000299]
    stage_status:
      segmentation: done
      concepts: in_progress
      assertions: pending
```

规矩：你只改自己批次、自己工位那一格；改成 `done` 的前提是校验 PASS 且 result 为 completed。

### 4.4 大书的期望节奏（防止一口吃）

第一遍只跑 3 个批次 → 人工抽查 → 修正任务模板 → 再放量。任何 agent 不得一次领取超过派发者指定数量的批次。错误会复制：模板有问题时跑得越多废得越多。

## 第 5 章 各工位详细规程

每个工位四件事：目标一句话 → 输出格式 → 通过/不通过样例 → 本工位容错表。

### 工位 1：转录核对

**目标**：让转录文本与原书页图逐字一致，并建立页码映射。（本项目优先复用外部平台转录，本工位主要是"核对"不是"录入"。）

输出：`transcript_vN.md`，页边界用 `<!-- p0012 -->` 注释标记；疑难字用 `⟦?⟧` 包裹并在 result 的 uncertainties 里逐个登记。

| 通过 | 不通过 |
|---|---|
| 与页图逐字一致，含异体字原样保留 | 把异体字/繁体"顺手"改成通行字 |
| 看不清的字标 `⟦?⟧` | 看不清的字凭上下文补一个"合理的字" |
| 缺页处标 `<!-- MISSING p0013 -->` 并 blocked | 跳过缺页继续，页码悄悄错位 |

容错：图片模糊 ≥ 整页 → blocked；个别字模糊 → `⟦?⟧` ＋ uncertainties，继续。**任何"我觉得应该是这个字"都是不通过。**

### 工位 2：结构盘点（见第 4.1 节，此处不重复）

### 工位 3：语义切分

**目标**：把原文切成语义完整的段，一个字不改。

输出：`segments`（YAML），每段 `seg_id / text / note`，类型 D 加 `layer / attached_to`。

**通过样例（示意，类型 A）**：

```yaml
segments:
  - seg_id: s01
    text: 陰陽順逆妙難窮，二至還鄉一九宮。
    note: 一联，总起阴阳顺逆与二至换局
```

**不通过样例及原因**：

```yaml
# 错 1：改了字（難→难）——TXT_001，整段作废
  - text: 阴阳顺逆妙难穷，二至还乡一九宫。
# 错 2：切在半句（联被腰斩，语义不完整）
  - text: 陰陽順逆妙難窮，
# 错 3：两段拼接后比原文少了一句——覆盖检查会抓
```

硬性检查：所有 text 按顺序拼起来（去掉你自己加的换行）必须等于输入原文。交付前必须自跑：
`python3 validators/check_segments.py <任务包目录> --type <文本类型>` ，PASS 才许交（SEG_001 覆盖、SEG_002 半联、SEG_003 编号、SEG_004 空字段）。

容错：不知道在哪切 → 先按类型细则（第 3 章）再试一次；仍不确定 → 在两个候选切点处都标注 uncertainties 选一个执行（切分不确定属于可修正问题，不升级）；发现原文疑似有缺漏乱序 → blocked。

### 工位 4：术语识别

**目标**：把段落里出现的术语链接到受控词表（glossary.yaml），只许匹配，不许发明。

输出：`concept_mentions`，每条 `seg_id / surface（原文写法）/ concept_id（词表里的）`。

| 通过 | 不通过 |
|---|---|
| "天蓬"→ 词表里的 `qimen.star.tianpeng` | 词表里没有"天英"，就自己编 `qimen.star.tianying` 塞进去 |
| 词表没有的词 → 写进 result 的 `new_concept_candidates`，不占 concept_id | 把普通词硬链接到术语（"难穷"不是术语） |
| 同形不同义按上下文选（"食神"在命理和"食"在饮食语境不同）拿不准 → uncertainties | 拿不准也硬选一个 |

容错：new_concept_candidates 是正常输出不是错误；一段里新词超过一半 → 可能词表版本不对，blocked 并说明。

### 工位 5：主张提取（全流程风险最高，规则最严）

**目标**：把段落里"原书主张了什么"提取成一条条独立命题，每条绑定证据。

前置规矩：本工位**双路独立**——你不会看到另一个模型的结果，另一个模型也不会看到你的。照实提取即可，分歧由第三方比对。

输出：`assertions.yaml`（格式见 `schemas/core/SCHEMA.md` 第 4 节）。

**通过样例（示意，类型 A，取《滴天髓》名句"甲木參天，脫胎要火"）**：

```yaml
- proposition: 甲木旺盛参天之势，初生（脱胎）阶段需要火
  relation: supports
  evidence:
    - source_span_id: ss_ditiansui_ed01_p0003_s01
      support_type: direct
  conditions:
    - 论甲木；"脱胎"所指阶段依注家有异（见 uncertainties）
  exceptions: []
```

**不通过样例及原因（每一条都是真实高发错误）**：

```yaml
# 错 1：加了原文没有的知识（原文只说"要火"，没说丙丁之别）
  proposition: 甲木脱胎要丙火，忌丁火
# 错 2：漏掉否定词——原文"不可例推"提成了"可以例推"，意思反了
# 错 3：把注家的话当正文主张（layer 是 commentary 却没标 school/注家归属）
# 错 4：把两个主张合并成一条（"要火"和"喜金"是两条，各自绑各自的证据）
# 错 5：evidence 为空、或引用了别的段（SEM_001 / REF_001）
# 错 6：把条件写丢——原文"春月之木"限定被省略，主张变成了全年通用
```

自查清单（交付前逐条过）：

1. 每条主张遮住 proposition 只看 evidence 的原文——原文真的这么说了吗？
2. 原文里的限定词（月令、旺衰、得使、贵贱、若/凡/惟/独）都进 conditions 了吗？
3. 原文里的否定（不、勿、忌、莫、非）方向对吗？
4. 这条是正文说的还是注家说的？层标对吗？
5. 一条里有没有藏着两条？

容错：某句实在读不出主张（纯叙事/过渡句）→ 不提取即可，不是错误；两种读法都通 → 三级容错出 ESC；整段与上文强关联无法独立理解 → blocked 要上下文。

### 工位 6：白话释义

**目标**：把原文翻成现代白话，供 APP 标注"机器释义"展示。

| 通过 | 不通过 |
|---|---|
| 逐句对应，原文说多少译多少 | 顺手补充背景知识（"这里的火指的是十神中的食伤"——原文没说） |
| 拿不准的词照抄原词加引号 | 拿不准的词换成一个具体的现代解释 |
| 保留原文的不确定性（"或云"译成"也有说法认为"） | 把"或云"译成肯定句 |

红线：释义**不许出现任何吉凶判断的强化**。原文"凶"就译"凶"，不许扩展成"非常凶险、务必小心"。

### 工位 9：词条聚合

**目标**：把同一主题的多来源内容聚合成一个 APP 词条。

| 通过 | 不通过 |
|---|---|
| 两派观点冲突 → 并列展示，各带出处 | 挑一派写成结论，另一派删掉或降格成"也有人认为" |
| 只用状态达标的 assertion（machine_extracted 以上，disputed 需带争议标记展示） | 引用 status 为 deprecated 的内容 |
| 每个知识点后紧跟出处编号 | 词条末尾垒一个总参考书目就完事 |

## 第 6 章 复核 agent 的工作方式（当你的任务是检查别人）

1. **不看生产者的推理过程，只看原文和结果**——从任务包 `input/` 重新读原文，逐条核对输出；
2. 每条给出判定：`agree / disagree / uncertain`，disagree 必须贴出你依据的原文；
3. 你无权修改对方的文件，只输出 `review.yaml`；
4. 你与生产者必须是不同家族的模型——如果发现自己被安排复核同家族产物，result 填 blocked 说明；
5. 复核通过 ≠ 升级状态：状态升级由程序在双方一致时自动执行，你不改 status 字段。
