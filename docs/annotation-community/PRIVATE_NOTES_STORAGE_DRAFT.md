## 2. 拟采用的三条独立路径

1. **本地保存**：Drift 保存账号隔离的笔记、修订、引用和操作状态；先成功落盘再报告已保存，离线可继续编辑。
2. **端到端设备同步**：通过既有配对与 LAN/WebRTC 能力同步同账号已授权设备；需要同步修订、附件、删除标记和关系，而不只是当前 Markdown 正文。
3. **云端备份**：复用云通道与对象存储，长期保存可恢复的加密版本。建议客户端加密、云端保存密文；启用开关与调度复用既有设置，默认是否自动开启需结合宿主当前设置确认。已允许该能力不等于用户已选择自动上传每份历史。

“已保存”“已同步到某设备”“已云备份”分别显示，不以任意一条通道成功冒充全部成功。长时间无设备在线也应能够完成已启用的云备份。

## 3. 对服务端数据草案的修正

- 共同的 Note/Revision/Anchor 是逻辑模型，不意味着私人内容要作为明文 Firestore 文档上传。
- 私人备份建议用独立 `private_note_backup` 实体/命名空间：外层最少包含 owner scope、不透明备份/修订 ID、协议版本、密文对象引用、密文哈希、加密与密钥版本、同步所需版本依赖和完成状态。恢复封装字段由存储维护者确认；不自行设计密码协议。
- Markdown、标题、选中原文、锚点、附件名称、@与修订差异均进入加密载荷；不在公共日志、通知或明文索引中泄漏。外层不可避免暴露的大小/时间/版本关系需要明确列出。
- 私人内容的全文检索和差异展示在授权客户端完成；此前提议的 Python difflib 仅适用于服务端可读的已发布内容，不能要求服务器比较私人密文。
- 公开发布由客户端显式选定一个修订，向公共发布 API 提交该修订的可公开内容；后端校验后生成 shared 策略的发布投影。一个逻辑 content_id 保持两端讨论身份，但私有修订与公开投影分存、分策略。
- 私有到公开是显式发布动作，不直接把私有 Blob 改权限，也不公开整条私有版本链。后续私人编辑仍走私有策略。
- 收回公开：关闭公共投影访问，保留私人数据和备份；不声称已公开过的数据重新获得“服务端从未读过”的加密保密性质。
- 私人同步事件不产生面向其他用户的评论/@通知；公开发布、公开评论和回复仍走已约定业务 outbox 与推送链路。

## 4. 同步、备份与恢复的必要门槛

- 长期备份与一次性 relay 数据在对象路径、用途、保留状态、清理规则上可区分；relay 完成不能删除仍在使用的备份。
- 同一修订经 P2P 和云端到达时去重；并发编辑保存多个分支或进入冲突处理，不能用时间戳覆盖历史。
- 备份清单只在所有修订/附件对象就绪并校验后标为完整，恢复使用完整快照与依赖；中断重试不破坏上一份完整备份。
- 验证“原设备还在”的设备迁移与“原设备全部丢失”的云恢复两种场景。每设备独立 DEK 的已有实现本身不能证明后者可恢复。
- 恢复密钥获取、设备授权/撤销、轮换和账号密码改变行为依照存储系统既有协议；若尚缺就列为工作包前置，不能改成服务器托管明文密钥来伪装 E2EE。
- 检查 row 与 blob 的真实加密边界，不能因为 StoragePolicy 写 e2eeOverSse 就认为所有行已加密；本地整库加密也不由 BlobCipher 自动提供。
- 验收需真实两设备同步、真实云端上传/下载、重启恢复、断网重试、重复投递、并发分支、账号隔离、私密转公开/收回及可理解的密钥不可恢复状态。纯 Fake 通过不算接通。
